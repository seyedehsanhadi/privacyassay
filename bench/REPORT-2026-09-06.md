# Supercookie investigation — 6 September 2026

The deployed supercookie failure was reproduced in Chrome with third-party cookies blocked. The storage-only run measured 29 of 30 readings (97%), left `storageCarry` as `ERR:storage-incomplete`, and assigned grade I. The candidate completed all 30 readings with score 13/100. **100% coverage means this experiment completed; it does not mean 100/100 privacy or exhaustive vulnerability detection.**

The user's 31-reading setup also includes WebRTC. A final live check of that combination is pending authorization to contact `stun:stun.l.google.com:19302`. It must not be described as a completed 31/31 live verification.

At investigation time, the public main page and companion were byte-identical to the original local page (SHA-256 `90c65ca3d2fa43b2950dd81eef4fd540a84aa6e955f91ce35d3f4b804208e9d1`). Candidate tests used the real HTTPS origins with HTML response overrides confined to disposable browser profiles. These measurements preceded deployment. Each candidate capture records its source hash.

## What was wrong and what changed

- Blocked storage getters lost their `SecurityError` classification. Explicit denials now remain distinct from unexpected failures.
- A silently rejected secure cookie was recorded as a broken probe. Exact cookie-name/token readback now establishes whether that write was retained.
- Chromium can return a generic Cookie Store write error. That error alone still earns no credit. A successful top-level read showing no token, followed by a successful identical write/read control, is required to establish a context-specific refusal. The control runs after the carryover read to avoid planting a false positive. See [Chromium's implementation](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/cookie_store/cookie_store.cc).
- Readback could race the writes, and the frame's deadline could erase a successful token before readback. Reads now wait for the writes; cleanup follows completion or failure. The Run button stays unavailable while the comparison is active.
- The detailed category could retain an old unknown result after rescoring, and unknown rows could display “no supercookie carried.” Headline, category and exports now use the updated result; missing or invalid readbacks remain unknown.
- IndexedDB errors retain their cause and aborted transactions settle. A confirmed absent WebGPU adapter now marks both identity and limits unavailable; genuine read failures remain unknown.
- Cache checks require a valid server counter. Missing static-host cache support is listed separately from persistent-storage failures and never changes the score.
- A script-blocked page now explains why Run is unavailable. The report's outcome label describes measured results instead of asserting a browser strategy or population uniformity.

Detailed JSON captures are retained locally and are not included in the public repository because they contain browser diagnostics. The table above summarizes their results.

The preserved captures include candidate snapshots taken during the investigation, identified by their source hashes; they are not a claim that every configuration was retested after every presentation-only edit.

Release validation also passed all 11 stress checks, including six consecutive audits, rapid clicks, viewport extremes, and static-host fallback. Vivaldi and Tor were retried before publication and retained the same blockers. Mullvad returned an incomplete export on retry; it also exposed an unsupported Goanna identity inference from missing worker/push APIs. That inference was removed and covered by a browser regression. The stress harness now waits for the comparison to release the Run button before starting its next audit.

Deployment requirement: both hosts must serve matching candidate files before public visitors receive the fixes; the GitHub companion-sync workflow verifies their hashes. Remaining limits: obtain authorization for the exact live WebRTC configuration and resolve the browser initialization/script/network blockers before assigning those browsers scores. This investigation does not establish that all possible bugs or privacy vulnerabilities have been eliminated.
